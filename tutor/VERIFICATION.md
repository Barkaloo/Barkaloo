# Проверка Barkaloo Tutor

## Постоянные коды учеников — 16 ноября 2026

По требованию пользователя вход учеников заменён на постоянный шестизначный код.
Преподаватель создаёт аккаунт через «Добавить ученика», ученик при первом входе
выбирает ник и оформление. Email и одноразовые приглашения в новом потоке не нужны.

| Первый вход | PASS | В отдельной браузерной сессии введён код, выбраны ник и светлая тема |
| Повторный вход | PASS | После выхода тот же код открыл тот же аккаунт с ником и двумя попытками |
| Учебный прогресс | PASS | Реальный ученик выполнил домашнюю работу и отметил модуль изученным; преподаватель увидел результат |
| Замена | PASS | Новый код сохранил ведущий ноль, старый код отклонён, прежний сеанс потерял доступ к RPC |

Использовался только временный технический аккаунт. Преподаватель работал в
своей существующей сессии 127.0.0.1, ученик — на localhost с отдельным Auth storage.
Обе стороны обращались к живым Supabase Auth, Edge Function и PostgreSQL.
Это полноценный ученический вход, отдельный от преподавательского предпросмотра.
Подтверждение почты ученику не отправляется и не требуется.

Миграция `20261116165804_tutor_persistent_student_codes.sql` применена; Edge Function
`tutor-student-access` развёрнута с собственной проверкой кода и авторизации
административных действий. Дополнительных платных сервисов не подключалось.
Auth/SMTP других проектов не менялись. Приватные ключи и коды не включены в обычный
data/export. В браузер не передаются служебный ключ и секрет шифрования.

`codes.test.mjs` проверяет AES-GCM, ведущие нули, изменение шифротекста, HMAC,
идемпотентное создание, роли, поколения сеансов, приостановку, архивирование и
лимиты на настоящем PostgreSQL PGlite. Старые интеграционные сценарии также
применяют пятую миграцию и проходят. Серверный TypeScript проверяется отдельно.

Первый вызов новой функции во время проверки получил временный upstream 503.
Форма показала ошибку, ложного успеха и лишнего аккаунта не было. После обновления
страницы повторное создание завершилось; последующие реальные входы прошли.
В deno.json закреплены npm-версия и nodeModulesDir:auto для воспроизводимой сборки.

На основном опубликованном домене проверен отдельный вход тем же аккаунтом:
восстановились ник, светлая тема, две попытки и завершённый модуль. В одном
запросе облачный upstream снова ответил 503; повтор успешно открыл аккаунт.
Клиент теперь выполняет один автоматический повтор при сетевом сбое/502/503/504
только для login/create/show. Создание идемпотентно по request_id; замена кода и
изменения доступа автоматически не повторяются. Таймаут отдельного запроса — 20 с.

Описанные ниже проверки UUID-приглашений и почты относятся к первоначальной
версии второго этапа. Текущий пользовательский поток использует постоянные коды.

Живой Supabase дополнительно проверен `supabase/tutor-stage2-smoke.sql`: запросы
исполняются с ролью authenticated и разными auth.uid(), данные и временные Auth
пользователи откатываются транзакцией. Изолированный тест `teaching.test.mjs`
применяет все миграции к PostgreSQL PGlite и покрывает двух преподавателей,
ученика, постороннего, RLS Storage, неизменяемость снимков и отзыв роли.

Браузер использовал существующую сессию преподавателя и встроенный предпросмотр.
Ответы отдельного технического ученика для проверки преподавательских экранов
отправлены через настоящий RPC с его auth.uid() из SQL Editor. Отдельный вход
реального ученика по паролю в браузере и доставку регистрационной почты эта
проверка не подтверждает.

Проверка выявила и исправила два случая: потерю выбранной даты при повторном
рендере формы и одинаковый now() у попыток в одной транзакции. Даты читаются из
полей при отправке; новые попытки используют clock_timestamp(). История не
переписывалась. Исправление базы вынесено в отдельную миграцию.

Файлы миграций синхронизированы с живыми версиями
`20261116125459` и `20261116131158`. Существующие таблицы и политики English/Fit
не изменялись. Security Advisor: новых WARN/ERROR нет; пять INFO без политик
относятся к закрытым таблицам ключей/приглашений; прежнее предупреждение Auth
о проверке утёкших паролей сохраняется.

После проверки удалены только точные UUID временных ученического аккаунта,
карточки, двух домашних работ, занятия, темы, модуля, заданий, приглашений и семи
попыток. Итог: 0 учебных модулей, попыток, учеников, домашних работ и занятий;
исходный профиль преподавателя и 27 разделов сохранены. Количество строк и
отпечаток политик `app_state` до/после очистки совпали. Новых файлов в Storage
эта проверка не загружала.

### Публикация второго этапа

Коммит приложения `9ee7704eb650f7eebf3e353f0ff9c5c4d16b9b39` развёрнут отдельным
проектом `barkaloo-tutor` на Node.js 24. Production deployment
`dpl_DvLLSUXMHE2Z4RHUgXADXyhT2S6K` имеет статус READY. Короткий домен
`barkaloo-tutor.vercel.app` назначен этому проекту как подтверждённый production
домен: `/` возвращает 307 на `/tutor/`, `/tutor/` — 200 без учётной записи Vercel.
Стандартная защита тестовых размещений сохранена.

В браузере по короткому адресу отобразилась русская форма Supabase Auth. Без
авторизации загружаются JavaScript/CSS; SHA-256 главного JS, CSS и компонентов
Students/Homework/Lessons совпали с проверенной локальной сборкой. Заголовки
CSP, nosniff и X-Frame-Options: DENY присутствуют. Домены English/Fit продолжают
указывать на прежний production deployment `dpl_FMDWdPqffRmr62i7bpikuKQAXva6`;
ветка main по-прежнему `f7ce376410664229a829c457647725fa13ba43b5`.

Публичные настройки Supabase Auth подтвердили: email включён, регистрация
разрешена, автоматическое подтверждение выключено. Новые аккаунты требуют
письма подтверждения; доставка и whitelist redirect URLs не проверены. Shared
Auth/SMTP не менялись, чтобы не затронуть вход English/Fit. Это остаётся отдельным
условием готовности регистрации реальных новых учеников.

Ограничения: общий RPC пока без пагинации; посещаемость не отделена от даты
занятия; «Проверена» не означает, что все ответы верны; поздние ответы допустимы.
Группы, платежи и выполнение программ не реализованы. Полный коммерческий
многопользовательский сервис и нагрузочное тестирование не заявляются.

Автотест `tutor/test/database.test.mjs` применяет миграции к настоящему
PostgreSQL в PGlite. Для Supabase-специфичных auth.uid и Storage-схемы задаются
минимальные окружения; проверка ответов и политики исполняются самим PostgreSQL.
Это не проверка доставки почты и не имитация успешного облачного развёртывания.
Работа с живым Supabase отдельно проверяется `supabase/tutor-smoke.sql` с ROLLBACK.

В первой попытке запуска двух старых archive-тестов Windows CRLF нарушили
побайтовое сравнение исходника и архива. Подтверждено, что после замены CRLF→LF
байты полностью совпадают. `.gitattributes` фиксирует LF для этих файлов;
содержание исходников English не менялось. После нормализации — 103/103 PASS.

Расширенный тест ручной проверки нашёл конфликт имени PL/pgSQL-переменной feedback
со столбцом. Исправление вынесено в отдельную миграцию; затем все типы ответов и
ручная проверка прошли. Имена файлов миграций синхронизированы с версиями,
зафиксированными MCP в supabase_migrations.schema_migrations.

В UI использовалась явно техническая временная тема, а не учебные материалы ЕГЭ.
Тестовые тема, модуль, задание, две попытки и прогресс удалены по точным UUID с
проверкой владельца. Один загруженный PNG из репозитория остаётся в приватном
Storage без ссылок из материалов; после удаления модуля его запрещают политики
чтения. В этой версии нет UI удаления неиспользуемых загрузок. Storage metadata
не удалялась прямым SQL, чтобы не создавать потерянные файловые объекты.

На момент проверки первого этапа ученические карточки, назначения, домашние
работы и журнал ещё отсутствовали. Их проверка описана выше. Публикации первого
этапа сохранили доступ всем вошедшим ученикам; его можно изменить в конструкторе.

Ограничения аудита: в существующей инфраструктуре есть предупреждения о sharp и
проверке утёкших паролей (см. README). Проверки не являются нагрузочным тестом,
аудитом внешнего SMTP или независимым пентестом.
